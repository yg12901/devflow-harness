## 评审要点

先 `git diff --stat` 看规模，再 `git diff` 看内容。然后拿上游产物对照着审，而不是凭感觉挑刺：

| 维度 | 看什么 |
|---|---|
| 正确性 | 边界条件、空值、溢出、并发竞态 |
| 契约 | 接口签名/错误码变了吗？调用方同步了吗？ |
| 资源 | 申请与释放是否配对，异常路径上会不会泄漏 |
| 兼容 | 老数据、老配置、灰度期间新旧共存 |
| 可测 | 新增逻辑有测试吗？是真验证还是走过场？ |
| 一致性 | 命名、错误处理、日志风格和周边一致吗 |
| 冗余 | 注释掉的死代码、无归属 TODO、复制粘贴 |

严重级分三档：🔴 必修（错误行为/崩溃/数据问题/安全）、🟡 建议、🔵 可选。**严重级要诚实** —— 什么都标 🔴 等于没有优先级。

## 产物

`04-review.md` 含 **问题清单** 和 **评审结论** 两章，每条问题带 `CR-01` 编号、`文件:行号`、问题描述、修改建议。结论必须是三选一的明确定级：**可合并** / **有条件合并** / **需打回**。

`04-review-response.md` 按 CR 编号分节，每条给出 **采纳**（附真实改动位置）/ **拒绝**（附技术理由）/ **后续迭代**（说明为何不在本次做）。

## 硬约束

- 首轮评审**不给最终定级**，必须经过 developer 逐条决策再复核
- 🔴 必修项**不允许标"后续迭代"** —— 要么改，要么给充分技术理由拒绝
- 拒绝理由必须是技术性的，"不想改""没时间"不算
- 复核只看增量 diff，不重新全量评审
- **第 3 轮强制收敛**，定级为「有条件合并」并列出剩余分歧，**禁止第 4 轮**
- 改完要重跑构建：`{{ commands.build }}`（门禁也会独立重跑）
