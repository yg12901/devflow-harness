### `02-design.md`
五个章节缺一不可：**现状分析**、**方案比选**、**推荐方案**、**影响范围**、**实施计划**。

方案比选要给 2-3 个候选，各自写清优势、代价、改动范围，然后**明确推荐一个并说明理由**。禁止"各有优劣请用户选"。

### `dependency-map.yaml`
三层结构，**每条必须带 `evidence` 写明搜索命令和命中位置**：

```yaml
core:          # 需求直接要改的文件
  - file: <路径>
    reason: <为什么是核心>
    evidence: "<你执行的搜索命令> -> <命中结果>"
associated:    # 调用了 core、可能被波及的文件
  - file: <路径>
    reason: <怎么被波及>
    evidence: "..."
observation:   # 实现同一接口的兄弟类，改动模式应保持一致
  - file: <路径>
    reason: "..."
    evidence: "..."
```

`core` 为空会直接判门禁失败 —— 那意味着没做代码探索。

### `tasks.yaml`
需求清单 + 任务清单 + 覆盖率矩阵。每个任务带 `depends_on` / `files_to_modify` / `acceptance` / `completeness_contract` / `status: pending`。末尾追加一个 `type: quality_gate` 的收尾任务。

### `impact-report.md`
含 **影响概览** 和 **影响明细** 两个章节，每条影响给出风险等级（高/中/低）。

### `knowledge-base.md`
增补探索发现，并在知识更新日志里加一行。

## 门禁会校验这些（提前对照，别等打回）

除常规的文件存在与章节完整外，S2 内置 9 项任务拆分结构校验：

1. 每个需求编号至少被一个任务覆盖，`uncovered_requirements` 为空
2. 每个任务都能追溯到需求，`orphan_tasks` 为空
3. `dependency-map.yaml` 里 `core` 的每个文件都被某任务的 `files_to_modify` 覆盖
4. `associated` 的每个文件要么被修改，要么登记在某任务的 `completeness_contract.must_notify` 里
5. `depends_on` 构成的依赖图无环
6. 所有 `depends_on` 指向真实存在的任务 ID
7. 单任务改动文件数 ≤ 5（超了继续拆）
8. 每个非 quality_gate 任务都有 `acceptance`
9. 存在 `type: quality_gate` 的收尾任务

另外：所有任务 `status` 必须是 `pending`。非 pending 说明架构师越权写了代码。
