## 执行方式：逐条做，不要一把梭

读 `tasks.yaml`，按 `depends_on` 拓扑排序，一条一条来：

```
对每个 status == pending 且依赖已 completed 的任务 T：
  1. 读 T 的 completeness_contract
       must_notify   —— 逐个文件检查是否真受影响，记录结论
       must_preserve —— 实现时确保不破坏这些约束
  2. 实现代码
  3. 按 T 的 acceptance 自验
  4. 把 T 的 status 改成 completed（直接改 tasks.yaml）
  5. 在 03-changes.md 追加本任务的执行记录
```

第 4 步每条做完就改、立刻落盘。这是断点续跑的依据 —— 会话中断后重新进来，看 `tasks.yaml` 就知道做到哪了。

## 构建验证

所有任务完成后执行：

```
{{ commands.build }}
```

失败就修，修完重跑。**连续 5 轮还不过就停下来**，返回 `status: blocked` 并附最后一次的完整错误输出。反复失败通常意味着方案层面有问题，需要人来看，别在这儿耗。

> 注意：门禁会**独立重跑一次**这条构建命令，用退出码判定。在产物里写"构建通过"但实际没跑，会在门禁处直接暴露，反而多耗一轮。没跑就写没跑。
