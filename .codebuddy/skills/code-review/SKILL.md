# 代码评审

评审不是「读 diff 找不顺眼的地方」，而是拿三份上游产物对照着看实际代码：

- `tasks.yaml` —— 每个任务的 `acceptance` 达成了吗？`must_preserve` 破坏了吗？
- `impact-report.md` —— 列过的影响点，代码里处理了吗？
- `02-design.md` —— 实现和推荐方案一致吗？偏离了有没有写进变更记录？

## 范围不止于新增行

1. 被改函数里**没改的行**也在范围内 —— 这次改动可能重新暴露那里的问题。
2. **被删的行**在范围内 —— 说出它原来守的是哪条行为，再到新代码里找这条行为重建了没。
3. **调用方**在范围内 —— 签名或语义变了，调用点同步了吗？

先 `git diff --stat` 看规模，再 `git diff` 看内容。说不清 `文件:行号` 的意见不要提。

## 评审维度

| 维度 | 看什么 |
|---|---|
| 正确性 | 边界、空值、溢出、并发竞态 |
| 契约 | 接口签名 / 错误码变了吗？调用方同步了吗？ |
| 资源 | 申请与释放是否配对，异常路径会不会漏 |
| 兼容 | 老数据、老配置、灰度期间新旧共存 |
| 可测 | 新增逻辑有没有真验证，还是走过场 |
| 一致性 | 命名、错误处理、日志和周边是否一类 |
| 冗余 | 注释掉的死代码、无归属 TODO、复制粘贴 |

## 问题怎么写

每条一个 `CR-NN` 编号，定级三档：

- 🔴 **必修** —— 会导致错误行为、崩溃、数据问题、安全隐患。不改不能合。
- 🟡 **建议** —— 可维护性、可读性、潜在隐患。可在后续迭代。
- 🔵 **可选** —— 风格偏好，不改也行。

严重级要诚实。什么都标 🔴 等于没有优先级。

模板：

```
### CR-01 🔴 必修
- 位置：`src/foo.cpp:128`
- 问题：<一句话，当前代码会怎样>
- 依据：<对照了哪条 acceptance / 哪条影响点 / 哪段旧行为>
- 建议：<开发可以执行的改法>
```

禁止：

- 改代码（那是 developer 的事）
- 「这里应该没问题」「开发大概考虑过了」
- 首轮就给合并定级（必须等 developer 逐条决策后再复核）
- 把建议项写成必修来凑条数

## 复核

开发对每条 CR 的决策只能是：采纳 / 拒绝（附理由）/ 后续迭代。
复核时只看：必修项是否都落地，拒绝理由是否站得住。
不要在复核轮突然冒出一批新的必修项，除非是开发改动引入的新问题。
