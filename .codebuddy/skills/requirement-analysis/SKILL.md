# 需求分析

交付物不是需求复述，而是下游能直接干活的结构化输入：
S2 靠 `R-*` 编号做覆盖率矩阵，S5 靠验收标准写用例。
一条不能被测试证伪的「需求」，等于没拆。

## 五类信号，逐句标

不要顺着原文抄一遍。逐句过，碰到就停下来标注，每条带来源原句：

| 信号 | 长什么样 | 怎么处理 |
|---|---|---|
| 模糊 | 「优化一下性能」「体验更好」 | 转成可量化指标；量化不了就进待澄清 |
| 假设 | 默认了某个前提但没说 | 显式写出来，标明是否已用代码验证 |
| 关联 | 会牵动其他模块或既有功能 | 记入影响范围，用 `code-explorer` 搜代码确认 |
| 反面 | 失败 / 异常 / 边界没提 | 主动补齐；问不清就按保守策略定义并标假设 |
| 缺量化 | 没说阈值、超时、上限、精度 | 进待澄清，给出建议默认值 |

零条待澄清通常意味着没读进去，不是需求写得特别清楚。

## 一条需求点只做一件事

```
R-01 <一句话：做什么>
     验收：<可观测的判定条件>
     来源：<原文哪一句>
```

「顺便再改个 xx」必须拆成独立编号。编号是全流程锚点，改编号等于让后面的覆盖率和用例对不上。

## 验收条件要能写成测试

用「做完之后能观察到什么」写，不用「实现某某功能」写。

| 差 | 好 |
|---|---|
| 支持按用户限流 | 同一 user 在窗口内超过配额的请求被拒绝，未知 user 返回满额 |
| 配置热更新生效 | 修改配额配置后，下一次 `Allow()` 使用新值，不必重启进程 |
| 性能更好 | P99 延迟不超过现有单桶路径的 1.2 倍（建议默认，待澄清） |

S5 拿到这条，应该能直接写出一个会失败的用例，再去证明它变绿。

## 影响范围必须搜代码

每个 `R-*` 至少有一次真实搜索。搜不到就写「未找到相关实现，可能是全新模块」+ 试过的命令。
禁止编一个仓库里不存在的路径。定位方法见 `code-explorer`。

## 不要越权

- 不写技术方案、不选实现、不写代码
- 不确定的写进待澄清，禁止「也许 / 大概齐 / 我猜」
- 有歧义且会改变方案的，宁可 `blocked` 问人，也不要替用户做产品决策
