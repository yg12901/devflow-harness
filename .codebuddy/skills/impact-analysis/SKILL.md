# 影响分析

AI 最容易漏的不是「要改的那个文件」，而是没人明说、改了就出事的地方。
本 skill 专门找那些。

## 五个维度，逐项问

对每个 `core` 改动点问一遍：

| 维度 | 要问自己什么 |
|---|---|
| 代码逻辑 | 改了 / 删了哪些方法？谁依赖原来的行为？ |
| 接口契约 | 签名、返回值、错误码变了吗？调用方要不要同步改？ |
| 状态与时序 | 初始化顺序、生命周期、并发访问有没有隐含假设？ |
| 功能完整性 | 原有的边界处理、日志、监控点，新方案保留了吗？ |
| 兼容性 | 老数据、老配置、灰度期间新旧共存会怎样？ |

每一条都要有代码依据。想不起来就回去跑 `code-explorer`，不要用常识填空。

## 风险等级

| 等级 | 含义 | 例子 |
|---|---|---|
| 高 | 漏处理会直接出故障或破坏兼容 | 公开接口语义变了，调用方没改 |
| 中 | 漏处理会在特定路径出错 | 异常路径上资源没释放 |
| 低 | 风格 / 命名 / 可观测性不一致 | 新日志字段和周边格式不同 |

「高」必须写清**检查方式**（跑哪条测试、看哪个调用点、对比哪份旧数据）。

## 落到任务上

影响点不是写完报告就结束。对每个 associated 文件，二选一：

- 这次就要改 → 放进某个任务的 `files_to_modify`
- 这次不改但必须确认没被波及 → 放进该任务的 `completeness_contract.must_notify`

两条都不占 = S2 的 CHECK-4 会失败。

`must_preserve` 写的是**不许被这次改动破坏的行为**，不是愿望清单。
一条 `must_preserve` 应该能被测试或评审直接打回。
