# 测试设计

本阶段只回答一个问题：**`01-requirement.md` 里每条验收标准，是不是真的被验证过了。**

## 先对照，再补洞

1. 抽出所有 `R-*` 验收条件，列成表：已有用例 / 需新写 / 无法测（写原因）。
2. 先搜现有测试，按项目已有风格写，不要另起一套目录和命名。
3. 用例名或注释里标出对应的 `R-*`，否则报告无法回链，门禁会打回。

## 什么叫「真验证」

一条用例必须在「功能没实现」时失败。只断言「函数没崩」「返回值非空」不算覆盖。

| 差 | 好 |
|---|---|
| 调用 `Allow()` 不崩溃 | 超配额后下一次 `Allow()` 返回拒绝 |
| 新文件能链上 | 未知用户拿到满额，已跟踪用户用尽后拒绝 |
| 跑了测试套件 | 对照表里每一条验收都指向具体用例 |

还要满足：

- **可独立跑** —— 不依赖其他用例的顺序和残留状态
- **覆盖边界** —— 正常路径之外至少有边界值和异常输入
- **测当前代码** —— 新增测试文件往往改了构建配置；先跑 profile 的 `build`，再跑 `test_unit`。直接测会打到上一阶段的陈旧产物

## 失败怎么处置

- 用例写错了 → 修用例，重跑
- 代码确实有 bug → `failed`，附失败用例和完整错误，由 leader 打回 developer
- 环境问题 → 写出命令、报错、判定依据，`blocked`。**禁止**把失败说成「预存在的环境问题」然后放行

最多修 3 轮。还不行就停。

## 未覆盖必须诚实

对照表允许「未覆盖 + 原因」。硬凑一个假用例会把缺口带到线上。
未覆盖且验收是本次范围的硬条件 → 不要把阶段标成 completed。

命令从 prompt 里的 profile 表取。门禁会独立重跑 `build` 和 `test_unit`，
报告里的「全部通过」不作数。
