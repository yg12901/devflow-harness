# 发布单

读者不是你自己，是出事时不在场的人。四个章节都要能脱离本次对话独立使用。

## 四章分别写什么

**变更内容** —— 改了什么、波及哪些模块、对应哪些 `R-*`。不要贴 git log。

**发布方式** —— 全量 / 灰度 / 分批，以及具体操作顺序。
profile 配了 `release.mr_create_command` 就执行；没配就写明需要手工创建，
并给出建议标题和描述。不要发明仓库里不存在的发布命令。

**验证方式** —— 发布后怎么确认功能正常：看哪些指标、哪段日志、怎么构造一条验证请求。
「观察一下」不算验证方式。

**回滚方案** —— 本章是发布的最后一道保险，门禁会检查它不为空，也不能写「无 / 暂无 / 不需要」。

## 回滚必须可执行

假设执行回滚的人没看过这次改动。至少写清：

1. 退到哪个版本 / 哪次提交 / 哪份配置
2. 执行什么命令或点哪个开关
3. 多久生效（进程重启？配置热加载？流量切走？）
4. 怎么确认退成功了
5. 回滚本身会不会丢数据或中断请求，调用方要不要配合

配置回退、功能开关、双版本共存，都算回滚，但都要写出步骤。
写「回滚即重新发布旧包」而不写旧包在哪、谁来发，等于没写。

## 安全默认

`release.dry_run` 为 `true`（默认）时：**只生成发布单，不真正触发发布流水线。**
需要真发布，由用户改 profile，不要在本阶段自行打开。

提交信息用 profile 的 `vcs.commit_template`。在当前分支提交，不建新分支。
