# 代码探索

目标不是「把仓库翻一遍」，而是对当前需求交出一份**带证据的模块理解**。
每条结论必须能回溯到一次真实搜索或一次真实读文件。

## 什么时候用

- 需求提到某个功能，但还不知道代码从哪进、从哪出
- 要写 `dependency-map.yaml` 或影响范围，需要 `文件:行号`
- 下游说「漏改调用方」——说明上次探索浅了，重做本 skill

## 四步，每步都留证据

按顺序走，不要跳。搞不清楚的写进「遗留问题」，不要假装理解。

1. **找入口** —— 这个功能从哪个函数 / 接口 / 命令进入。
   证据：`grep` / 符号搜索的命令原文 + 命中位置。
2. **追调用链** —— 从入口追到输出。记下数据怎么变、状态在哪里改、错误怎么返回。
3. **看架构** —— 这块用了什么分层或抽象、兄弟实现有哪些、为什么这么分。
4. **挖细节** —— 关键算法、错误路径、已有测试覆盖到哪。只对真正会改的那一块下钻。

原则：**宁可深入搞懂一个模块，也不要浅尝五个。**

先读 `.codebuddy/devflow/repo-map.md` 里的热点文件和模块分布，决定从哪儿下手，
不要一上来全仓盲搜。

## 证据格式

依赖地图和影响范围里，每条都写成：

```
evidence: "<你执行的搜索命令> -> <命中文件:行号>"
```

反例（门禁和下游都会被带偏）：

- `src/foo.cpp`（没有命令、没有行号）
- 「应该在限流模块附近」（没有搜索）
- 编一个看起来合理、仓库里并不存在的路径

搜不到就写「未找到相关实现，可能是全新模块」，并给出你试过的命令。

## 三层怎么填（给 S2 用）

| 层 | 放什么 | 不放什么 |
|---|---|---|
| `core` | 需求直接要改的文件 | 只读了一眼的文件 |
| `associated` | 调用了 core、签名或语义变化会波及的文件 | 「也许有关系」的文件 |
| `observation` | 同一接口的兄弟实现，改动模式应对齐 | 无关的同类命名 |

`core` 为空 = 没做探索，S2 门禁会直接失败。
