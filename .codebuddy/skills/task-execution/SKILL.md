# 任务执行

工单是 `tasks.yaml`，不是设计文档。按 `depends_on` 拓扑排序，一次只做一条
`status == pending` 且依赖都已 `completed` 的任务。

## 一条任务的闭环

```
1. 读 completeness_contract
     must_notify   → 逐个文件看这次改动是否真波及，记下结论
     must_preserve → 实现时当作测试约束，不许破坏
2. 只改 files_to_modify 里的文件
3. 按 acceptance 自验（能跑的命令就跑，不要用「应该没问题」代替）
4. 立刻把该任务 status 改成 completed，写回 tasks.yaml
5. 在 03-changes.md 追加本任务分节
```

第 4 步必须当场落盘。会话中断后唯一可靠的进度是磁盘上的 `tasks.yaml`，
不是对话记忆。做完三条再一起改 status = 中断后那三条都得重做。

## 边界

- 发现要改的文件不在 `files_to_modify` 里 → **停下来**返回 `blocked`，说明要扩哪些文件。
  擅自扩大范围等于绕过 S2 的结构校验。
- 方案做不通 → `blocked`，由 leader 决定是否回退 S2。不要自己改方案继续做。
- 不创建、不切换分支。在当前分支提交。
- 构建 / 测试命令只从 prompt 里的 profile 命令表取。

## 整体构建

全部任务 `completed` 之后，跑 profile 的 `build`。失败就修，修完再跑。
**连续 5 轮仍失败**就 `blocked`，附最后一次完整错误输出。
反复失败多半是方案问题，耗在这里没有意义。

门禁会**独立再跑一遍**同一条构建命令。产物里写「构建通过」但没跑，
会在门禁处直接暴露，还白白多一轮。没跑就写没跑，跑挂了就写挂了。

## 影响范围确认

`impact-report.md` 里每一条都要有结论：检查了没问题 / 检查了已同步处理。
存在未处理项，S3 门禁会打回。这不是走形式，是把架构师的隐性影响收到实现里。

## 被打回时

leader 会附上门禁失败项。**只针对失败项改**，不要把已 completed 的任务重做一遍。
