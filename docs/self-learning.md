# 自学习闭环

## 为什么原型的「自学习」不够

原型已经有了事件日志、经验库和分级注入，看起来闭环是完整的。但实际跑下来有两个洞：

1. **蒸馏要人手动跑。** 高频问题不会自己浮上来，得有人记得去执行蒸馏命令。
2. **注入之后没人回收效果。** 一条经验写进 P0 就永远在那儿，每次运行都消耗 token，
   但没有任何机制判断它到底有没有用。经验库只进不出，最后变成一个越来越大的、
   没人敢删也没人细看的文本块。

第二点是更根本的问题。一个不会遗忘的学习系统，本质上不是学习系统。

## 完整闭环

```
   ┌──────────────────────────────────────────────────────────┐
   │                                                          │
   ▼                                                          │
 采集 ──────▶ 蒸馏 ──────▶ 分级 ──────▶ 注入 ──────▶ 有效性回收 ┘
门禁失败    按签名聚类    跨 run 频次   拼进 prompt    注入后还失败吗
自动落事件   生成候选      P2→P1→P0                    ↓           ↓
                                                    没用         有用
                                                  降级/淘汰    固化 proven
```

### 1. 采集 —— 不依赖 Agent 自觉

门禁每次判 FAIL，`runner.run_stage_gate()` 自动调 `record_gate_failures()`，
把每个阻断项写成一条事件。回退、重试同理。

这一步的关键是「自动」。原型里记录事件要 Agent 主动调命令，
而 Agent 在失败的时候恰恰是最不可能记得上报的。

事件落在 `learnings/events/YYYY-MM-DD.jsonl`：

```json
{"at":"2026-09-18T13:11:02","run_id":"DEMO-01","stage":"S2",
 "event_type":"gate_fail",
 "signature":"gate_fail:S2:CHECK-1:需求覆盖完整性",
 "detail":"CHECK-1:需求覆盖完整性：未覆盖需求 ['R-02']（声明的未覆盖项 []）",
 "fix":"每个 R 编号必须至少落到一个 task，否则需求会在实现阶段静默丢失",
 "tags":["gate","S2"]}
```

### 2. signature —— 归因的锚点

`signature` 是整套机制的枢纽，它把三样东西对齐：

- **事件**：这次哪里失败了
- **经验**：哪条经验是针对这个问题的
- **后续门禁结果**：注入那条经验之后，这个问题还在不在

格式是 `gate_fail:<阶段>:<检查项>`。手工记录的事件没有显式签名时，
用 `<类型>:<阶段>:<detail 的 md5 前 8 位>` 兜底 —— 只按「类型+阶段」会把
同一阶段的不同问题错误地聚成一簇，蒸馏出来的经验会变成几个问题的糊状混合体。

有了精确签名，效果归因才不靠模糊的文本相似度匹配。

### 3. 蒸馏与分级

`devflow distill` 按签名把事件聚类，命中次数达到阈值就生成候选经验，
然后按「跨多少个不同需求复现」定级：

| 级别 | 条件 | 注入策略 |
|---|---|---|
| P2 | 新生成 | 标签匹配时注入 |
| P1 | 在 ≥2 个不同 run 中复现 | 匹配阶段时注入 |
| P0 | 在 ≥3 个不同 run **且** ≥2 个不同阶段中复现 | 每次必注入，`stage` 自动改为 `*` |

阈值在 `workflow.yaml` 的 `learning` 段里配。

分级的意义是控制 prompt 体积：偶发问题不该占用每次运行的 token 预算，
而跨阶段反复出现的问题说明它是系统性的，值得让所有角色都知道。

### 4. 注入

`devflow next` 装配 prompt 时调 `learning.query(stage, tags)`，
按 P0 → P1 → P2 排序，同级内命中次数多的靠前，标记为「待改写」的靠后，
最多取 8 条。同时调 `record_injection()` 记下这次注入了哪些 —— 这是下一步归因的依据。

### 5. 有效性回收 —— 补上的关键一环

门禁跑完后，`learning.feedback()` 拿本阶段的注入记录和门禁结果做归因：

```
对每条本阶段注入过的、且签名与本阶段相关的经验：

  这次门禁在同一签名上又失败了？
    ├── 是 → fail_after_inject += 1，effective_streak 归零
    │        累计 2 次 → 降一级 + 标记 needs_rewrite
    │                   （说明这条经验没抓住问题本质，描述得改）
    │        累计 4 次 → 淘汰（retired，不再注入）
    │
    └── 否 → effective_streak += 1
             连续 3 次 → 标记 proven，固化，不再参与降级
```

这一环让经验库能自我收敛：

- 有用的经验往上走，最终固化
- 没用的经验往下走，最终淘汰
- **「降级 + 标记待改写」而不是直接删**，因为问题本身是真实的，
  只是当前的描述没起作用。`devflow reflect` 会把这些条目列出来，
  提示 `knowledge-engineer` 重写它。

`origin: manual` 的条目不参与自动降级 —— 人工写入的铁律由人负责维护。

### 6. 复盘

`devflow reflect` 在流水线结束时跑，做三件事：蒸馏、统计本轮事件分布、
列出待改写和已淘汰的条目。

## 亲眼看一遍

演示脚本的最后一段专门演示这个闭环：

```bash
./examples/run-demo.sh /tmp/devflow-demo
```

会看到这样的输出：

```
━━ 第二条需求：同一个坑再踩一次，看经验库怎么反应
   ✗ S2 门禁再次因 CHECK-1 打回（同一个签名，第 2 次出现）

   ↳ devflow distill
     扫描 5 条事件，聚成 2 个签名簇
     ✓ 新沉淀经验：L-005
     ✓ 优先级提升：L-005  P2 → P1
       依据：在 2 个 run / 1 个阶段复现

   这条新经验从下一次运行开始就会被自动注入 S2 的 prompt：
     [L-005|P1] CHECK-1:需求覆盖完整性：未覆盖需求 ['R-02']
              对策：每个 R 编号必须至少落到一个 task…
              统计：命中 2 次，跨 2 个需求
```

## 手工维护

`learnings/active.yaml` 可以直接编辑，格式是人可读的。

```bash
devflow learnings --stage S2     # 看会注入到 S2 的经验
devflow learn --stage S3 --type pitfall \
  --detail "<问题模式>" --fix "<对策>" --tags "cpp,api"
devflow distill --dry-run        # 先看蒸馏会做什么
devflow reflect                  # 看哪些经验需要改写
```

## 写好一条经验

唯一的判断标准：**下次遇到相似情况，这条经验会不会改变某人的做法。**

描述**模式**，不是**实例**：

| ❌ 实例（下次用不上） | ✅ 模式（可复用） |
|---|---|
| `token_bucket.cpp:78 没判空指针` | 限流器的 `Allow()` 在配置未加载时会拿到空指针，新增限流器实现时都要处理这个时序 |
| 本次改了 3 个文件 | 按 key 分桶的组件，查询接口用 `operator[]` 会隐式创建元素，让只读操作改变状态 |
| 构建失败了两次 | 新增源文件忘记登记到构建配置时，编译会通过但代码根本没被编进去 |

经验库应该随代码一起入库（`install.sh` 生成的 `.gitignore` 刻意不忽略它），
这样团队成员共享同一份积累。忽略的只有 `runs/`（每次运行的状态与产物）。
