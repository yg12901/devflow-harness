# 架构与设计决策

## 三层分层

devflow 能跨部门复用的前提是把「流程」「技术栈」「引擎」三件事彻底拆开。

```
┌─────────────────────────────────────────────────────────┐
│ L3  流程层    config/workflow.yaml                       │
│     七个阶段、每阶段谁负责、产出什么、门禁校验什么         │
│     —— 换流程改这里，不碰引擎                             │
├─────────────────────────────────────────────────────────┤
│ L2  适配层    config/profiles/*.yaml                     │
│     构建怎么跑、测试怎么跑、发布怎么发、红线命令有哪些      │
│     —— 换部门/换技术栈改这里，不碰引擎和流程               │
├─────────────────────────────────────────────────────────┤
│ L1  引擎层    engine/*.py                                │
│     状态机、门禁原语、prompt 装配、自学习闭环              │
│     —— 完全不认识 cmake / gtest / git，只认识 profile 里的键 │
└─────────────────────────────────────────────────────────┘
```

判断分层是否成立的检验标准：**把 `profiles/default.yaml` 里的 `cmake` 换成 `go build`，
整条流水线应该照常工作，引擎和七个角色定义一行都不用改。** 目前满足这个条件。

## 七个角色

```
                      ┌──────────┐
                      │  leader  │  编排者：调度、跑门禁、裁决推进
                      └────┬─────┘  自己不产出任何阶段产物
       ┌───────────┬───────┼───────┬───────────┬──────────┐
       ▼           ▼       ▼       ▼           ▼          ▼
  requirement  architect  developer  code-    test-    knowledge-
   -analyst                          reviewer engineer  engineer
      S1          S2      S3/S6/S4响应   S4       S5         S7
```

`developer` 承担三段工作（S3 编码、S4 评审响应、S6 发布），因为这三段都是
「按既定输入改代码/提交」性质的执行动作，拆成三个角色只会增加上下文传递成本。

任务拆分的结构完整性（需求覆盖、孤立任务、依赖成环、核心文件是否都有任务认领等）
是确定性的集合运算和图遍历，交给 `gates.py::run_plan_check()` 执行。
文档更新和经验沉淀都在流程末端，由 `knowledge-engineer` 一次写完，保证两边对得上。

### 自查悖论

演示里有个刻意设计的场景：架构师产出的 `tasks.yaml` 漏了需求 R-02 没拆任务，
而它自己填写的 `coverage_matrix.uncovered_requirements` 却是 `[]`。

这不是编出来的极端情况，而是**让同一个主体既做事又自查时的必然结果**：
模型漏掉覆盖和它误以为自己没漏，是同一个认知错误的两面，不会互相纠正。

`plan-check` 的 CHECK-1 不读那个声明值，而是拿 `requirements` 和
`coverage_matrix.requirement_to_task` 做集合差运算。这才是有效的检查。

结论推广开就是：**能用确定性运算验证的约束，绝不交给 LLM 自查。**

## 状态模型

一次运行的全部状态在一个文件里：`runs/<run_id>/run-state.json`。

```
run-state.json
├── run_id / title / type / profile / status
├── current_stage
├── context              跨会话恢复的核心
│   ├── requirement_summary
│   ├── technical_decisions
│   ├── key_files
│   ├── last_summary     下游阶段靠它拿上游结论，不必重读全文
│   └── blockers
├── stages{}             每阶段：status / 耗时 / 尝试次数 / 门禁分 / 摘要 / 产物
├── transitions[]        阶段流转历史（含回退原因）
└── events[]             最近 200 条事件
```

状态只写这一份文件，所有读写都走 `RunState`。会话中断后只认这一处，
不会出现进度记录和产物目录互相矛盾、要人来判断该信哪个的情况。

### 中断恢复

最常见的中断形态不是进程崩溃，而是 **subagent 静默死亡**：turn 耗尽、
沙箱超时回收、收尾动作被截断，`task()` 返回空或没有 `status` 字段。

遇到这种情况时跑 `devflow inspect`，不要停下来等用户说「继续」：

```
读该阶段的期望产物清单 → 逐个检查文件是否存在且非空
  ├── complete  产物齐备   → 直接跑门禁推进，不要重跑（重跑会覆盖已完成的工作）
  ├── partial   做了一半   → 带着已完成部分重调，只补缺失的
  └── empty     什么都没有 → 提高 max_turns 重新调用
```

核心判断是：**产物是比 subagent 返回值更可靠的进度证据。** 返回值会丢，
文件不会。

## 门禁引擎

### 声明式

引擎实现约 10 个通用原语，`workflow.yaml` 声明用哪些：

| 原语 | 用途 |
|---|---|
| `file_exists` / `file_nonempty` | 产物存在性与最小篇幅 |
| `sections_present` | 必需章节（`all_of` / `any_of` + `min_any`） |
| `regex_present` / `regex_absent` | 编号存在、禁用措辞 |
| `yaml_valid` | YAML 可解析且顶层是映射 |
| `yaml_path_nonempty` / `yaml_path_empty` | 正反两向的路径约束 |
| `yaml_items_field` | 列表每项的字段取值（如所有任务必须 completed） |
| `command_ok` | **真正重跑一条 profile 命令，用退出码判定** |

加一道门禁是加几行 YAML，不用改引擎代码。

### 独立复算

校验「构建是否通过」不能靠在 `changes.md` 里搜索成功字样 ——
那行字是 LLM 自己写的，等于让被考核者填自己的成绩单。
模型完全可以在没跑过构建的情况下写出格式完美的构建日志。

`command_ok` 直接执行 `profile.commands.build`，看退出码。S3、S4、S5 各有一道。
配套地，各角色的 prompt 里都明写了「门禁会独立重跑，自述不作数，没跑就写没跑」——
既然伪造一定会被拆穿，诚实反而是成本最低的选择。

profile 没配对应命令时按 `on_missing` 降级为 `WARN`（记录但放行），
而不是假装检查过了。演示里 S6 得 75 分就是因为 `release_check` 未配置 —— 
**能力缺失就如实反映在分数上**。

## Prompt 装配

`devflow next` 输出的 prompt 已经装配好四样东西，leader 原样透传即可：

1. **上游摘要** —— 不是文件路径。下游多数情况不需要重读上游全文，
   给摘要能省掉大量 token 和往返。需要细节时 prompt 里也给了产物路径。
2. **匹配到的历史经验** —— 按阶段和标签从经验库里选，P0 全局注入，
   P1 匹配阶段，P2 匹配标签，最多 8 条。
3. **仓库地图提示** —— 每个阶段只提示它该看的部分（如 S2 看热点文件和模块分布）。
4. **profile 的真实命令** —— 让 Agent 不用猜「这个项目该用什么命令构建」。

## 自学习

见 [self-learning.md](self-learning.md)。一句话概括：
门禁失败自动采集，按签名蒸馏分级后注入下一轮 prompt；
注入后仍失败的经验会降级淘汰，连续有效的会固化，经验库自己收敛而不是无限膨胀。

## 已知边界

诚实地说清楚它做不到什么：

- **发布是 dry-run 默认。** 引擎不会替你真的触发发布流水线，
  除非你在 profile 里显式配命令并关掉 `dry_run`。
- **回退不撤销代码。** `rollback` 只清空流水线状态，不会 `git reset`。
  代码要不要回滚由人决定。
- **经验蒸馏的文字质量依赖 `knowledge-engineer`。** 自动蒸馏能把高频问题聚出来、
  定好优先级，但「把问题描述成可复用的模式」这件事仍需要模型来做。
  自动生成的条目 `pattern` 字段是原始门禁证据，比较粗糙。
- **并发。** 状态写入有文件锁，但同一个 run 不支持多个 leader 并发推进。
- **仓库地图是静态快照。** 代码大改之后需要重新 `devflow repo-map`。
