# 知识沉淀 — 按用户维度限流

## 可复用经验

### 1. 查询类接口必须声明 const 且不得隐式创建资源

- **模式**：给一个「按 key 分桶」的组件加查询接口时，最容易写成
  `Available(key) { return buckets_[key].available(); }` —— `operator[]` 会在
  key 不存在时**默认构造并插入**一个元素。结果是「查一下」这个只读动作
  悄悄改变了组件状态，还顺带撑大了 map。
- **对策**：查询接口一律声明为 `const`（编译器会强制你不能用 `operator[]`），
  未命中时走显式的只读分支返回默认值。并且为这条约束**单独立一个测试用例**守住它 ——
  这类 bug 不会让测试变红，只会在监控数据上表现为莫名其妙的内存增长。
- **适用范围**：所有 map/cache 类组件的查询接口。

### 2. 加新粒度用组合，不要改造现有类

- **模式**：需求是「在现有能力上加一个维度」时，第一反应往往是给现有类的方法加参数。
  这会破坏所有既有调用方，还让一个类同时承担算法和路由两个职责。
- **对策**：新增一个类，内部**组合**现有类作为单元。代价是多一个类型，
  收益是现有代码零改动、回滚时接入方可以直接退回旧类。回滚方案因此从
  「revert 代码」降级成「改一行接入代码」。
- **适用范围**：限流、缓存、连接池等「一个算法 + 多个实例」结构的扩展需求。

### 3. 拒绝评审意见时，把判断前提写进代码注释

- **模式**：评审提出的性能优化建议，在当前条件下确实不划算（本次是
  C++11 不支持 `try_emplace` 且对象只有 12 字节），但「当前条件」本身是会变的。
  只在评审响应文档里写理由，半年后没人会去翻。
- **对策**：拒绝的理由如果依赖某个前提，就在代码里加一行注释写明这个前提。
  后来者改动时能立刻知道「这里为什么这么写」以及「什么时候该重新评估」。

## 本次踩坑

### 门禁 CHECK-1 打回一次：覆盖率矩阵漏了 R-02

- **现象**：S2 首次提交的 `tasks.yaml` 只拆了 T1（对应 R-01），漏了 R-02，
  但 `coverage_matrix.uncovered_requirements` 里却填着 `[]`。
- **根因**：覆盖率矩阵是架构师手写的，**自查和被查是同一个主体**。
  模型一边漏掉了覆盖，一边在矩阵里声称自己没漏，两个错误互相掩盖。
- **拦截点**：`plan-check` 的 CHECK-1 不看声明值，而是拿 `requirements` 和
  `coverage_matrix.requirement_to_task` 做集合差运算，直接算出 `R-02` 没有承接任务。
- **教训**：**能用集合/图运算验证的结构性约束，绝不能交给 LLM 自查。**
  这也是本流水线把原来的「计划评审角色」替换成脚本的原因 —— 又快又不会因模型波动而漏判。

### 评审提出但本次未处理

`Available()` 对「未跟踪用户」和「恰好满额用户」返回值相同，调用方无法区分。
本次验收标准明确要求未知用户返回满额，所以实现正确。若后续监控需要区分，
再加 `IsTracked()`。记录在此供后续需求参考。
