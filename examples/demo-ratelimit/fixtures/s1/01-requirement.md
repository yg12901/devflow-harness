# 需求分析 — 限流器支持按用户维度限流

## 需求拆解

### R-01 按用户维度独立限流
当前 `TokenBucket` 是进程级单桶，所有调用方共享同一份令牌。需要支持以用户标识为键，
每个用户持有独立的令牌桶，互不影响。

- 验收：两个不同用户各自发起请求，其中一个用户耗尽令牌被拒绝时，另一个用户仍能正常放行。
- 来源：需求原文「同一个接口不同用户之间不应该互相挤占配额」。

### R-02 查询用户剩余令牌
需要对外提供查询能力，给定用户标识可以拿到该用户当前剩余令牌数，用于监控与排障。

- 验收：对从未出现过的用户查询，返回满额（等于桶容量）；对已消耗过令牌的用户查询，返回实际剩余数。
- 来源：需求原文「运维希望能看到某个用户当前还剩多少额度」。

## 影响范围

### R-01 影响范围
- `include/ratelimit/token_bucket.h:14` —— 现有 `TokenBucket` 类，将被复用为单用户的桶实现
- `src/token_bucket.cpp:7` —— `Allow()` 现有语义需保持不变，避免影响既有调用方
- `CMakeLists.txt:8` —— 新增源文件必须登记，否则不参与构建

证据：`grep -rn "TokenBucket" include/ src/ tests/` 命中 6 处，均在演示工程内部，无外部调用方。

### R-02 影响范围
- 与 R-01 落在同一新增类上，不额外牵动现有文件。

证据：`grep -rn "available()" include/ src/` 命中 1 处，仅 `TokenBucket::available()` 自身。

## 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 内存无界增长 | 中 | 每个新用户都会创建一个桶，用户数无上限时 map 会持续增长。本次不做淘汰，但需在文档中注明。 |
| 线程安全 | 中 | 现有 `TokenBucket` 明确不保证线程安全，新增的按用户 map 同样不加锁，沿用「调用方自行加锁」的约定。 |
| 语义回归 | 低 | 复用而非修改 `TokenBucket`，现有全局限流行为不受影响。 |

## 验收标准

| 需求 | 验收标准 |
|---|---|
| R-01 | 用户 A 耗尽令牌被拒绝时，用户 B 的请求仍被放行 |
| R-01 | 同一用户连续请求超过容量后被拒绝 |
| R-02 | 查询未出现过的用户，返回值等于桶容量 |
| R-02 | 查询已消耗令牌的用户，返回值等于实际剩余数 |

## 待澄清

1. **用户数上限与淘汰策略** —— 需求未说明。当前假设演示场景用户数可控，不做 LRU 淘汰。
   若线上使用需补充淘汰机制，否则存在内存增长风险。建议默认值：不淘汰，但暴露 map size 供监控。
2. **令牌补充的时间驱动方式** —— 需求未说明 `Tick()` 由谁驱动。假设沿用现有约定，由调用方按固定周期触发。
